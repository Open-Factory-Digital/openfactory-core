# Previews: what the deployment needs to show a change running

A project that declares `preview:` can have a card's change started as the **whole product** —
every service running, the ones the change touched built from it, the rest as they are on the base
branch — before its pull request merges. How a repository comes to declare one is
[ONBOARDING §11c](../ONBOARDING.md#11c--a-look-before-the-merge-previews). This page is the other
half: what the **deployment** needs so that a preview can run, and so that a browser can open it.

Every exposed service of a preview is served at its own host,
`<service>--<project>--<unit>.<preview domain>`, through the panel's own port and **never under the
panel's address**. A preview runs code nobody has reviewed yet; on the panel's host that code could
read the credential of whoever opened it. Everything below follows from that.

| you run | go to |
|---|---|
| the compose stack, opened as `localhost` | §1 |
| the compose stack on a server people reach by name | §1, then §2 |
| one machine, with no Docker by default | §3 |

---

## 1 · The compose stack: previews are on

The stack's own `docker-compose.yml` names what a preview needs, and a row in `.env.compose` says
otherwise:

| variable | on this stack | what it does |
|---|---|---|
| `OPENFACTORY_PREVIEW_RUNTIME` | `compose` | the worker runs each preview on this host's Docker daemon, through the compose plugin its image carries. `none` turns previews off, and every card then says so |
| `OPENFACTORY_PREVIEW_REACH` | `network` | a preview's exposed services sit on that preview's own internal network, and the worker connects the panel's container to it while it lives |
| `OPENFACTORY_PANEL_CONTAINER` | `openfactory-panel` | the container the worker connects — the panel service's `container_name` |
| `OPENFACTORY_PREVIEW_DOMAIN` | `preview.localhost` | the domain previews are served under. Chrome and Firefox send every `*.localhost` host to this machine, so it needs no DNS while the panel is opened as `http://localhost:8787` (Safari: §3) |
| `OPENFACTORY_PREVIEW_DOCKER_CONFIG` | `/var/lib/openfactory/docker` | the registry logins a preview pulls private images with — its own, never the worker's. `openfactory preview login <registry>`, run in the worker, writes one; use a read-only token, because anyone the panel lets into a project can start a preview that pulls with it |
| `OPENFACTORY_PREVIEW_SECRET` | generated by `init` | the key preview links are signed with. Empty is safe: the panel makes one per process, and a restart only sends an open preview's viewer back through the panel |
| `OPENFACTORY_PREVIEW_MAX` | `4` | how many previews run at once; a start past it is refused on the card, naming the previews that are up |

Then ask the worker, which holds the daemon a preview runs on:

```bash
docker compose --env-file .env.compose exec worker openfactory doctor myapp
docker compose --env-file .env.compose exec worker openfactory preview prove myapp
```

`doctor` says whether the runtime has what it needs — the daemon answers, the compose plugin works
with the pull-credential directory, the panel's container is running, the preview domain is set, and
the work directory the worker writes is the one the daemon mounts — and, per project, whether the
names the registry lists for its previews are in the worker's environment and whether its name
would share a preview's hosts with another project's. `preview prove` brings the project's base
product up once, waits until it is ready, and takes it down again: nothing a change wrote is built.

**What a preview reaches here.** Its own services, and the panel's container, which joins the
preview's edge network to proxy it — nothing else: not the internet, not the engine or the worker,
not another preview. Builds are the exception: a Dockerfile's `RUN` lines are run by the daemon,
with the internet. A service that needs something outside at run time — an identity provider, a
package fetched at start — needs a network the operator names for it:

```bash
docker network create openfactory-preview-egress
docker compose --env-file .env.compose exec worker \
  openfactory project set-preview myapp --network openfactory-preview-egress
```

The card of every preview that joins it says so. `bridge` and `host` are refused as that network.

**A preview reaches nothing of this host either** (#291). An `internal` Docker network alone does
not stop that: its bridge keeps an address on the host, and a container on it reached a service
listening on `0.0.0.0` of the host through it (measured on Docker Engine 29.1.3). So every network
a preview runs on is made with `com.docker.network.bridge.gateway_mode_ipv4=isolated`, which gives
the bridge no address on the host; the same measurement then reached none of the host's addresses,
and the preview's services still reached one another and the panel.

The daemon has to honour that option, and the worker checks that it does rather than trusting it:
before each preview starts it makes a network the same way and reads back whether it has a gateway,
and it reads back every network the preview then runs on. On an engine that refuses the option, or
takes it and leaves the gateway, **no preview starts**, and its card says why. The engine accepts
the option on internal networks only, which is why the one-machine reach below, whose published
network cannot be internal, says what it reaches instead.

**A network nothing uses any more.** A daemon may still hold a network called `openfactory-preview`,
from a build in which every preview shared one; `doctor` says so and prints the one command that
removes it.

## 2 · A server reached by name

A person opens `https://web--myapp--12.<preview domain>/` from a link on the card. For that address
to answer:

1. **DNS: one wildcard record.** Every preview host is a single label under the preview domain, so
   one record, `*.<preview domain>`, pointing where the panel is reached, covers every preview of
   every project.
2. **TLS: a wildcard certificate, in front of the panel.** Whatever terminates TLS for the panel
   also serves `*.<preview domain>` with a certificate for it, and forwards those requests to the
   panel's port with the request's `Host` header unchanged — the panel routes a preview by the host
   it was asked for — and with `X-Forwarded-Proto: https`.
3. **`.env.compose` says where the panel is and what the domain is:**

   ```bash
   OPENFACTORY_PANEL_URL=https://panel.example.com
   OPENFACTORY_PREVIEW_DOMAIN=previews.example.com
   ```

   The worker and the panel read the same rows: the worker writes each service's address into the
   others' environment (`OPENFACTORY_PREVIEW_URL_<SERVICE>`) with the panel's scheme and port, and
   the panel serves the hosts under that domain.

**The panel's credential over TLS.** Served over https — directly, or behind a terminator that
sends `X-Forwarded-Proto: https` — the panel's sign-in cookie is `__Host-openfactory_token`:
`Secure`, `Path=/`, no `Domain`. A browser refuses that prefix on any cookie a sibling host sets, so
a preview cannot plant one, and over TLS the panel reads no other spelling. On plain http the prefix
cannot be used and the plain `openfactory_token` is kept.

**Which preview domain you may use follows from that.** A page under a domain that shares the
panel's registrable domain is *same-site* with the panel, and a script there can set a cookie the
panel's host receives — fixing the credential a person then signs in with. `__Host-` closes that;
plain http does not:

| the panel (`OPENFACTORY_PANEL_URL`) | the preview domain | |
|---|---|---|
| `https://panel.example.com` | `previews.example.com`, or a domain of its own | allowed |
| `http://panel.example.com` | anything under `example.com` | **refused** — `openfactory doctor` fails on it and says both ways out |
| `http://panel.example.com` | a registrable domain of its own, `example-previews.com` | allowed |
| `http://localhost:8787`, or an IP address | any | allowed |

A preview domain under `localhost` is always allowed: nobody but this machine can reach it. The
rule is read from `OPENFACTORY_PANEL_URL`, so write the address people actually use.

**The application's own host check.** The router forwards the browser's `Host`, so an application
that checks it — Django's `ALLOWED_HOSTS`, Rails' `config.hosts` — must allow the preview domain on a
named deployment; the preview proposal for such a project says so in its pull request.

**What the router does not carry.** WebSockets: a development server's live-reload channel does not
reach the browser through a preview. A first page gets up to three minutes (the registry's
`upstream_timeout_seconds`, 180 by default) before the router answers *"still starting"*, so a
terminator in front should not cut the request sooner.

## 3 · One machine: off until you opt in

The one-machine door needs no Docker, and previews stay off there: `openfactory init` writes
`OPENFACTORY_PREVIEW_RUNTIME=none` into `~/.openfactory/env`, and every card says there is no
preview on this deployment and names the four lines that opt in. They are in the same file,
commented. With Docker installed, replace the `none` line with them:

```bash
OPENFACTORY_PREVIEW_RUNTIME=compose
OPENFACTORY_PREVIEW_REACH=loopback
OPENFACTORY_PREVIEW_PORTS=42000-42999
OPENFACTORY_PREVIEW_DOMAIN=preview.localhost
```

then start the factory again (`openfactory up`), and ask:

```bash
openfactory doctor myapp
```

**Read what opting in means before you do it.** `doctor` repeats it on every run, as lines that
pass — it is the deployment working as you chose — and every preview's card says what applies to
it:

- **The port range.** The panel is a process on this machine and cannot use Docker's own DNS, so
  each exposed service is published on `127.0.0.1` — never on every interface — at a port derived
  from its host name within `OPENFACTORY_PREVIEW_PORTS`. The panel derives the same port from the
  host a browser asks for; nothing is read back. A derived port something already answers on —
  another preview, a container, any program — fails the start by name, saying who holds it: stop
  that, or move or widen the range.
- **The key guards the panel's door, not the port.** A request through the panel without the
  preview's cookie is refused (401). But anyone on this machine, and the job box, can open a
  preview's port directly, without it.
- **What a preview reaches is measured, not promised.** Docker publishes no port from an internal
  network, so here a preview's edge network is a bridge with masquerading turned off, which would
  leave its outbound packets unanswered on a Linux engine. **On Docker Desktop it stops nothing**
  (measured on 29.1.3, macOS): a preview container reached the internet, and this Mac's own
  services bound to `127.0.0.1` through `host.docker.internal` — the panel (which `init` leaves
  without a token on a laptop), the engine, and other previews' ports without their key. The Mac's
  LAN address timed out. So at every start, once its data is in, a throwaway container on the
  preview's network asks whether it reaches the internet (`1.1.1.1`) and a listener this machine
  opens on `127.0.0.1` for the length of the question, and the card says what it found; `doctor`
  asks the same on a throwaway network. A question that cannot be asked is said as such, and the
  preview still starts. On a Linux engine nothing has been measured, and nothing is claimed in
  advance.
- **Safari.** Chrome and Firefox send every `*.localhost` host to this machine themselves; Safari
  asks the system's resolver. `doctor` asks this machine's resolver whether it answers a preview's host
  itself, and prints the `/etc/hosts` line either way, one per card you open:

  ```
  127.0.0.1 web--myapp--12.preview.localhost api--myapp--12.preview.localhost
  ```

  On macOS 26.6.2 the system resolver answered `*.localhost` itself; Safari was not driven.

None of this is a new reach on this door: the job box here already runs the agent's code as you,
with the same reach — which is why previews on one machine are yours to opt into, and said, rather
than refused.

Pull credentials on this door are Docker's own (`~/.docker`, where Docker Desktop keeps its logins
and its compose plugin) unless `OPENFACTORY_PREVIEW_DOCKER_CONFIG` names another directory.
